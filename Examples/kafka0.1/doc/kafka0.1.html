kafka0.1 — a drone telemetry broker

A minimal, runnable message broker built on a single append-only log. It decouples a fast telemetry producer from a slow database consumer, delivers events live, and survives a database crash without losing data — the core ideas of Kafka, implemented from scratch in Node.js.

01 — Overview

# What this is

kafka0.1 simulates a drone fleet sending telemetry faster than a database can absorb it. Instead of writing each event straight to MongoDB, every event is first appended to a durable log file. Independent readers then consume that log at their own pace: one streams events live to operators, another drains them into MongoDB.

The log in the middle is the entire point. It absorbs the rate mismatch between a fast producer and a slow consumer, and it acts as a buffer that holds events safely while downstream systems are slow, restarting, or crashed.

  • Decoupled — producers never wait on the database; a slow or dead consumer cannot block ingestion or live delivery.
  • Replayable — each consumer tracks its own offset and resumes exactly where it stopped.
  • Crash-safe — kill MongoDB mid-run and no data is lost; the log holds the backlog until the consumer catches up.
Scope

This is a teaching and prototyping build — faithful to Kafka's core mechanics (append-only log, offsets, decoupled consumers) but deliberately without partitions, replication, or segment indexing. Those are the 0.2 roadmap.

02 — Architecture

# How the pieces fit

One writer feeds the log. Two readers consume it independently — a realtime path and a durable path — that never block each other.

Single writer (producer) · one log · two independent readers (broker, consumer)

Critically, the realtime path has no database in it. The broker reads the log and pushes to clients, so live telemetry keeps flowing even while MongoDB is down. The durable path is the only one that touches Mongo, and it is allowed to lag.

03 — Design & guarantees

# What it promises, and how

PropertyGuaranteeMechanism
OrderingPer-log total orderSingle writer + monotonic integer offset = line number
Delivery (DB)Effectively onceIdempotent upsert keyed by _id = offset
Crash recoveryZero loss on DB outageConsumer never advances its offset on a failed write
DecouplingProducer never blocksProducer writes only to the log; never touches Mongo
Live deliveryDB-independentBroker fans out from the log over WebSocket
The three load-bearing decisions

A single writer removes write races and makes ordering free. Offsets turn "where was I?" into integer comparison, enabling replay. Idempotent writes make "resume from where I stalled" safe even if a write half-succeeded before the crash.

05 — Protocol & formats

# Wire & storage formats

Ingest — HTTP

The generator publishes a telemetry event to the producer:

POST:4001/publish
// request body
{ "droneId": "drone_101", "type": "BATTERY_LOW",
  "lat": 28.6139, "lon": 77.2090, "battery": 14, "ts": 1718000000000 }

// response
{ "offset": 42 }

Log line — on disk

Each event is one line: the offset, a tab, then the event JSON.

FILEdata/drone_events.log
40	{"droneId":"drone_103","type":"GPS_LOCK","battery":89,...}
41	{"droneId":"drone_101","type":"RTL_ENGAGED","battery":22,...}
42	{"droneId":"drone_101","type":"BATTERY_LOW","battery":14,...}

The broker pushes each new event to clients as a framed message:

Widen the gap

A faster generator and slower consumer make the buffering more dramatic — the log backlog grows visibly. Try GEN_INTERVAL_MS=20 CONSUMER_DELAY_MS=400.

07 — Operating

# Quick start

Requires Node 18+ and a local MongoDB listening on localhost:27017.

SHELLinstall
npm install

Start the five processes in separate terminals. Order matters only for the producer and broker, which own the ports.

  1. node with-kafka/2-producer.js — opens the ingest port and the log
  2. node with-kafka/3-broker.js — begins tailing the log for clients
  3. node with-kafka/4-consumer.js — starts draining to MongoDB
  4. node with-kafka/5-client.js — subscribes for live telemetry
  5. node with-kafka/1-generator.js — starts the telemetry stream

You will see the producer appending quickly, the client printing live events, and the consumer writing to Mongo slowly — its reported lag grows because the generator outpaces it. That growing lag, sitting safely in the log, is the buffer doing its job.

08 — Operating

# The crash test

This is the experiment the whole design exists for. With everything running, stop the mongod process and watch the two halves of the system diverge.

With the log (the broker system)

  • Producer, generator, broker and client are unaffected — telemetry keeps flowing.
  • The consumer logs mongo write failed … NO DATA LOST and backs off.
  • The log file keeps growing the entire time.

Restart mongod. The consumer resumes from its committed offset and drains the whole backlog. Nothing was lost.

Without the log (the naive baseline)

SHELLbaseline
node no-kafka/naive.js
# then stop mongod and watch:
# [naive] produced=120 stored=83 LOST=37   <-- DATA LOSS

Events produced during the outage have nowhere to wait and are gone permanently. Restarting Mongo only stores new events — the gap never fills.

The takeaway

Same crash, two outcomes. The only structural difference is the log sitting between the producer and the database. That buffer is the difference between a recoverable outage and permanent data loss.

09 — Operating

# Verifying no loss

Once the consumer has caught up, the document count in MongoDB equals the number of lines in the log:

SHELLverify
# count rows the broker system delivered to mongo
mongosh drone_sim --eval 'db.telemetry.countDocuments()'

# count events that were ever written to the log
wc -l data/drone_events.log

# the naive path will be short by exactly the events lost during the outage
mongosh drone_sim --eval 'db.telemetry_naive.countDocuments()'
10 — Reference

# Limitations

kafka0.1 is intentionally minimal. These are known and accepted for this version.

  • Single partition, single broker. No partitioning of the topic and no replication of the log — one machine, one file.
  • Whole-file reads. The consumer re-reads the log each loop and the producer scans it on startup — clear over fast, fine for a demo, O(file size).
  • One writeSync per message. A syscall per record caps throughput; there is no batching yet.
  • No retention. The log grows forever — no segments, rotation, or compaction.
  • In-memory subscriptions. Client subscriptions live in the broker's memory and reset on restart; clients receive only events from connection time onward (no historical replay yet).
  • No durability beyond the OS. Writes reach the page cache, not guaranteed to disk — there is no fsync and no replication.
