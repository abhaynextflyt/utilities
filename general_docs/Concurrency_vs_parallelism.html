Concurrency, parallelism & the event loop

Everything that sits between "JavaScript is single-threaded" and "this log broker writes 100 partitions at once." How async actually overlaps work, where the real parallelism comes from, and which lever to pull when — with the adjacent concepts you'll reach for next.

01 — Foundations

# Concurrency is not parallelism

These two words get smushed together and cause most of the confusion. They are different things.

  • Concurrency — dealing with many things at once by interleaving them. Tasks are in progress together, but a single worker can switch between them. It's a structure for handling overlap.
  • Parallelism — doing many things at the same instant, on separate workers (cores, disks, machines). Genuinely simultaneous execution.

A single chef juggling four pans is concurrent — one person, rapid switching, nothing burns. Four chefs each on one pan is parallel. Node's event loop is the one chef: spectacular at concurrency, incapable of parallelism on its own.

Concurrency is about structure — handling many in-flight tasks. Parallelism is about execution — running them literally at once. You can have either without the other.

02 — Foundations

# CPU-bound vs I/O-bound

This is the single most important lens. Before asking "how do I make this faster," ask what the task is waiting on.

TypeBottleneckExamplesWhat helps
I/O-boundWaiting on disk, network, DBAppend to log, HTTP, DB queryConcurrency — many ops in flight on one thread
CPU-boundDoing computationCompression, hashing, parsingParallelism — more cores running code

Appending to a log is I/O-bound: the thread spends its time waiting for the disk, not computing. That single fact is why a single-threaded Node process can keep a disk — or a hundred disks — fully fed. The work isn't on the CPU; it's on the hardware.

Async gives you concurrency of waiting. Threads and processes give you parallelism of working. Match the tool to which one you're short on.

03 — How JavaScript runs

# One thread, one callback at a time

Your JavaScript runs on exactly one thread. The event loop pulls one callback off a queue, runs it to completion, then pulls the next. Two JS callbacks never execute simultaneously in a single process — there is no preemption mid-function.

This is a feature, not just a limit: because nothing else runs while your function is on the stack, you never face data races on your own variables. The cost is that one long-running callback blocks everything behind it.

The crucial move is separating two mechanisms people conflate: the callback queue (serial, runs your JS one at a time) and async I/O (the actual disk/network work, done off your thread by libuv or the kernel). The queue is serial; the I/O underneath it is not.

04 — How JavaScript runs

# The event loop has phases

"The event loop" isn't one queue — it's a cycle through ordered phases, each draining its own queue before moving on. Knowing the order explains a lot of "why did this callback run before that one" surprises.

1 · timers
setTimeout / setInterval callbacks due now
2 · pending
deferred system callbacks (some errors)
3 · poll
retrieve I/O events; run their callbacks. The loop parks here when idle
4 · check
setImmediate callbacks
5 · close
close handlers (socket 'close', etc.)

The poll phase is where the loop spends its waiting time — blocked on the OS, asking "any I/O ready?" When a disk write finishes or a socket has data, its callback runs here. If nothing is pending, the loop sleeps here rather than spinning, which is why an idle Node server uses ~0% CPU.

05 — How JavaScript runs

# Macrotasks vs microtasks

Between every phase, Node drains two higher-priority queues completely before continuing. These are microtasks, and they jump ahead of ordinary callbacks.

  • process.nextTick() — drained first, before anything else, after the current operation.
  • Promise callbacks (.then, resolved await) — drained next, before the loop advances to the next phase.
  • Macrotasks — timers, I/O callbacks, setImmediate: one per loop turn, the phase-based queue above.
Footgun

A recursive process.nextTick or an unbounded promise chain can starve the loop — microtasks keep jumping the queue, so the poll phase never runs and your I/O callbacks never fire. Concurrency dies even though nothing is "blocking" in the CPU sense.

06 — How JavaScript runs

# Serial vs parallel dispatch — your choice

Issuing an async operation does not wait for its result. The call returns in microseconds and the work runs off-thread. So whether operations overlap is decided entirely by where you put your await — it is a choice, not a law.

await between each op serial — no overlap
op1
op2
op3
total ≈ t1 + t2 + t3
fire all, then await together parallel — overlapping
op1
op2
op3
total ≈ max(t1, t2, t3)
SERIALeach waits for the last
await op1(); await op2(); await op3();  // op2 starts only after op1 resolves
PARALLELdispatch first, collect after
const a = op1(), b = op2(), c = op3();  // all in flight now
await Promise.all([a, b, c]);            // collect already-cooking results

This maps straight onto partitioned writes: within a partition you await each write before the next (deliberately serial — that preserves order); across partitions you dispatch without awaiting between them (overlapping — that's the parallelism).

07 — How JavaScript runs

# Blocking the loop is the cardinal sin

Because all your JS shares one thread, a CPU-heavy synchronous function freezes the entire server while it runs — no I/O callbacks, no new connections, nothing. A 200ms JSON parse on a hot path adds 200ms of latency to every concurrent request.

Mitigations, in order of reach: break the work into chunks yielded with setImmediate; move it to a worker_thread; or offload to a native/streaming library that does the heavy lifting off-thread. The rule of thumb: keep individual callbacks short, and never do unbounded CPU work on the main thread.

08 — Under the hood

# libuv: the loop plus a thread pool

Node delegates all async work to libuv, a C library with two distinct engines. Understanding which engine handles which I/O explains every concurrency limit you'll hit.

Your JS
one thread, one callback at a time — dispatches and handles results
↓ hands off async work
libuv loop
network & timers — watched by the OS event notifier, no extra threads
libuv pool
disk (fs), DNS, crypto — a fixed pool of worker threads
↓ issues syscalls
OS + hardware
kernel, device queues, the actual disks & NICs that do the work

The split is the key insight: network I/O uses an OS notification mechanism and scales almost without limit on the single thread, while disk I/O is routed through a small, fixed thread pool. Same await syntax, completely different scaling characteristics underneath.

09 — Under the hood

# Network I/O: epoll and the C10k problem

Sockets don't use the thread pool. The OS provides an event-notification interface — epoll on Linux, kqueue on BSD/macOS, IOCP on Windows — that lets one thread watch thousands of connections and ask the kernel "which of these are ready?" in a single call.

This is what solved the historic C10k problem (handling ten thousand simultaneous connections). The old model used one thread per connection — 10,000 threads, crushing memory and context-switch overhead. The event-driven model uses one thread watching all 10,000 descriptors. It's the entire reason an event-loop server can hold enormous connection counts cheaply, and why network concurrency in Node is effectively unbounded.

10 — Under the hood

# Disk I/O: the fixed thread pool

File operations can't be watched the same way — historically there was no good "tell me when this file write is ready" primitive — so libuv runs them on a thread pool. Each fs call occupies a pool thread until it completes.

PropertyValueConsequence
Default size4Only 4 file ops execute at once; the rest queue
KnobUV_THREADPOOL_SIZEMust be set before the pool is created (process start)
Caphistorically 128, 1024 in modern libuvYou can raise it, but not arbitrarily
Also shares itDNS lookup, crypto, zlibA flood of fs can starve dns, and vice versa

So "fire 100 file writes" really means "100 submitted, ~4 running, the rest waiting for a free pool thread" — unless you raise the pool size. That's the software ceiling. But raising it only matters if the hardware underneath can actually do more at once, which is the next section.

11 — Under the hood

# io_uring — where this is heading

The thread-pool-for-disk design is a workaround for an old gap. Modern Linux closes it with io_uring: a true asynchronous interface for disk I/O, where the kernel completes file operations without tying up a worker thread, using shared submission/completion ring buffers.

Recent libuv versions use io_uring for some filesystem operations on Linux, which can lift disk I/O closer to the unbounded model network already enjoys — fewer thread-pool bottlenecks, higher concurrent-write ceilings. Worth knowing as a direction: the thread-pool limit you tune today is partly a historical artifact, not a law of nature.

12 — The hardware ceiling

# Hardware decides the real parallelism

Threads and pools are permission slips to use parallelism the hardware either has or doesn't. The thread pool lets you submit 100 concurrent writes; whether they execute at once is decided by how many independent devices exist underneath.

SetupResult
100 separate physical disksReal parallelism — 100 writes land at once, devices independent
100 files on one HDDNo gain — all funnel into one device queue and serialize; contention may make it worse
One fast NVMe SSDPartial — deep hardware queues overlap a dozen-ish; tune pool to queue depth, not partition count

Threads are not the parallelism. Independent hardware is. A thread pool is necessary but not sufficient — it can only feed parallelism the disks already provide.

Beyond the disks themselves, the path matters: enough PCIe lanes, controller bandwidth, and on big boxes NUMA locality (which CPU socket owns which device). "100 disks" only parallelizes if the bus feeding them isn't itself the bottleneck.

13 — The hardware ceiling

# Why append-only is fast: sequential I/O

There's a reason a log is append-only rather than a mutable structure. Sequential writes — always to the end of the file — are dramatically faster than random writes scattered across the device.

  • On a spinning disk, sequential avoids seek time — the head doesn't move. Random writes pay a seek per operation, often 100× slower.
  • On an SSD, sequential reduces write amplification and plays well with the flash translation layer; random writes churn the controller.
  • The OS can coalesce sequential writes into large, efficient flushes; it can't coalesce scattered ones.

This is the deep reason Kafka and your broker are built on a log at all: appending is the one disk access pattern that's cheap everywhere. "Just add to the end" isn't simplicity for its own sake — it's the fastest thing a disk can do.

14 — The hardware ceiling

# Durability: write() is not safe yet

A returned write() does not mean the data survived a crash. It usually lands in the OS page cache and is flushed to the device later (write-back caching). A power loss in that window loses it.

CallGuaranteeCost
write()In OS page cache, not durableCheap, fast
fsync()Data + metadata on the deviceExpensive — waits for hardware
fdatasync()Data on device, skips some metadataCheaper than fsync
O_DIRECTBypasses page cache entirelySpecialist; you manage caching
The lever that actually matters for a log

The expensive operation is the fsync, not the write. So the throughput question for a log isn't "how many writes in flight" — it's "how few fsyncs for how many records." Batch many appends per fsync per partition. This beats maximizing raw concurrent write calls, and it's how real brokers hit their numbers. Real durability ultimately comes from replication (a copy on another machine), not from fsync alone.

15 — The hardware ceiling

# Little's law — how many in flight?

A precise tool for sizing concurrency, borrowed from queueing theory:

in-flight = throughput × latency   ( L = λ × W )

To sustain 10,000 writes/sec at 2ms latency each, you need 10000 × 0.002 = 20 operations in flight at all times. That number tells you how big your pool or queue depth needs to be — no more, no less. Set the pool to 20-ish, not 1000. It also explains the ceiling: if the device can only hold so many in flight, your max throughput is bounded by that divided by latency. Stop guessing pool sizes; compute them.

16 — Scaling out

# Threads vs processes

When one core or one fault domain becomes the limit, you replicate the unit of execution. The two ways differ in what they share.

ThreadsProcesses
MemoryShared address spaceIsolated — separate memory
CommunicationShared variables (need locks)Message passing / IPC
A crashTakes the whole processContained to one process
CostCheap to spawn, lightHeavier — own heap, slower start
CorrectnessYou own race conditionsNo shared-memory races

Shared memory makes threads fast and dangerous; isolation makes processes safe and a little heavier. This tradeoff — not "which is real parallelism" — is the actual decision.

17 — Scaling out

# The GIL, and why languages differ

"Threading isn't real parallelism" is true for some runtimes and false for most. Threads are real parallelism in C, C++, Java, Go, Rust — two threads genuinely run on two cores. What blocks it in JS and Python is a runtime constraint, not a property of threads.

  • JavaScript — one execution thread per isolate. Workers don't share a heap by default. CPU parallelism needs separate isolates (workers/processes).
  • Python — the Global Interpreter Lock: only one thread runs bytecode at a time. Same outcome, different mechanism. (Being relaxed in newer "free-threaded" builds.)
  • JVM / Go / Rust — no such lock. Threads run truly in parallel within one process, sharing memory.

The precise statement: in GIL-style runtimes, threads don't give CPU parallelism, so you reach for processes. Elsewhere, threads do. It's about the runtime, not about threads.

18 — Scaling out

# Node's concurrency toolkit

Three ways to get more than one event loop, each for a different job:

ToolGives youUse when
clusterN processes sharing a listening portScale a server across cores; load-balanced connections
worker_threadsExtra threads, own isolate, can share memory via SharedArrayBufferCPU-bound work (compression, hashing) without leaving the process
child_processArbitrary separate processesRun other programs, full isolation, different runtimes

For an I/O-bound broker, cluster (or just separate process instances) is the idiomatic scale-out: one loop per core, each owning a subset of partitions. Reach for worker_threads only when per-record CPU work — not I/O — is the bottleneck.

19 — Scaling out

# Shared memory in JS: SharedArrayBuffer

Worker threads normally communicate by copying messages. For hot paths that's too slow, so JS offers SharedArrayBuffer — a block of memory visible to multiple workers at once — paired with Atomics for safe concurrent access (atomic reads/writes, compare-and-swap, and a lightweight wait/notify).

This is the one place JS hands you real shared-memory concurrency, with the real shared-memory hazards: you now need atomics and careful ordering, exactly like a threaded language. Useful for a shared counter or ring buffer across workers; overkill for most app code. Knowing it exists matters when message-copying becomes your ceiling.

20 — Scaling out

# Green threads & goroutines

Go's model is worth understanding as the contrast. Goroutines are cheap user-space "threads" (a few KB each) multiplexed by the runtime onto a small pool of real OS threads — an M:N scheduler (M goroutines on N OS threads, N defaulting to your core count).

The payoff: you write simple blocking code — a goroutine just does a blocking write — and the runtime parks it and runs another while it waits. You get the ergonomics of "one thread per task" with the efficiency of an event loop, plus real CPU parallelism because the underlying OS threads run on multiple cores with shared memory. It's why Go expresses "100 independent partition writers" directly, with no thread-pool tuning and no await-placement subtlety — the cost being that you now own shared-memory correctness (mutexes, atomics, races).

21 — Scaling out

# The three scenarios, evaluated

100 partitions, 100 disks. Same workload, three models. They are not equally good — and the right answer depends entirely on the bottleneck.

ModelStrengthWeakness
Node · 100 pool threadsSimplest; offsets are in-memory counters; zero coordinationOne event loop = CPU ceiling + single crash domain for all 100
Node · N processesReal CPU parallelism + fault isolationCross-process coordination (ownership, routing); memory; use ~1 per core, not 100
Go · 100 goroutinesCPU parallelism in one address space, no IPC tax, blocking-style codeYou own race safety; still one crash domain per process
  • Pure I/O-bound, 100 real disks → all three saturate the disks. The Node single-loop version is genuinely enough; more processes buy robustness, not throughput.
  • Per-record CPU work appears (compression, checksums) → the single loop starves the disks. Now you need multiple cores: Go in-process, or Node across processes.
  • Fault isolation (one bad partition mustn't kill 99) → only multiple processes help, in either language.

Threads/goroutines/pool-threads give concurrency of execution; independent disks give parallelism of writing; separate processes give fault isolation and, in Node, CPU parallelism. Pick by what you're short on — not by what sounds most parallel.

22 — Synthesis

# Partitions: the unit of everything

A partition isn't a performance trick bolted on — it's the structural unit that makes all three benefits possible at once.

  • Concurrency — N partitions are N independent ordered streams. They don't contend for one tail, so their writes overlap freely.
  • Ordering — within a partition you serialize (one in-flight write at a time), so per-key order is preserved. Across partitions there is no global order, by design.
  • Distribution — the partition is the unit you hand to a process, a disk, or a machine. This is the one that scales without limit.

Routing stays trivial regardless of scale: partition = hash(key) % N. A given drone's events always land in the same partition — preserving its order — no matter which process or machine owns that partition.

This is exactly how real Kafka scales, and why a single-threaded Node broker is closer to Kafka's model than it seems. Kafka doesn't write one partition with many threads either; it spreads partitions across multiple brokers, on multiple machines, on multiple disks. The parallelism lives at the partition/disk/machine level — the same lever you reach for in Node.

23 — Synthesis

# Amdahl's law: where scaling stops

Adding workers has a hard limit set by the part that can't parallelize. If 5% of the work is serial, the maximum speedup is 20×, no matter how many cores you throw at it — the serial 5% dominates.

For a broker, the serial fractions are the things every write must pass through: a single global offset counter, a shared metadata map, one coordinator. The design lesson is to shrink the serial part — per-partition offset counters instead of one global counter, shared-nothing partitions instead of shared state — so that adding partitions and machines actually buys near-linear scaling instead of hitting a wall.

You don't scale by adding workers. You scale by removing the thing they all have to wait on.

24 — Synthesis

# The decision framework

The whole manual collapses to one question asked in order: what is the bottleneck?

If you're short on…The symptomThe lever
I/O concurrencyOne op waits for the last; throughput low, CPU idleDispatch without awaiting between ops; raise pool / queue depth to Little's-law size
Disk parallelismPool full, all writes queue on one deviceMore independent disks / volumes — hardware, not software
CPUOne core pinned, disks idle, loop lagsworker_threads (Node) or true threads (Go); spread CPU work across cores
Fault isolationOne bug takes everything downMultiple processes, each owning a partition subset
DurabilityCrash loses recent writesBatch fsync per partition; replicate to another machine
Linear scalingAdding workers stops helpingRemove the shared serial point (Amdahl)

The hardware does the parallel work in every design. Threads, processes, and runtimes are just different-cost ways to feed it. Choose the cheapest one that clears your actual bottleneck.
